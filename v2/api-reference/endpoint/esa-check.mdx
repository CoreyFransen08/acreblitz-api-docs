## Response

`success` describes request handling. Read `compliance.status`, `processing_complete`, `soil`, `runoff`, `drift`, and `issues` for the assessment. `compliance.scope` is `requirements_and_gaps`; its `version` is the assessment format version, independent of the API URL version.

Product results include `esa_required`, registration status, effective pests, and PULA limitations. For ESA-required checks, the response also includes an opaque `application_event_id` and a `mitigation_portal_url` when available.

`mitigation_portal_url_expires_at` is the signed-link expiration in signed-link mode and null in token mode. `expires_at` describes the field portal's availability, which can have a different lifetime. Use the returned link unchanged.

## Runoff requirements and portal exemptions

When a product or PULA introduces an EPA runoff requirement, the API assumes runoff is required immediately. No portal questionnaire answer is needed to evaluate points: sufficient credits return `met`, a shortfall returns `not_met`, and missing scoring inputs return `indeterminate`.

Each `compliance.runoff[]` entry includes `required`, `exempt`, `required_points`, `label_required_points`, `earned_points`, `gap`, `status`, `credited_measures`, `runoff_exemption_claimed_at`, and `runoff_exemption_reasons`.

- With no exemption, `required: true`, `exempt: false`, and `required_points` equals the label/PULA point target in `label_required_points`.
- When the user saves an EPA runoff exemption in the portal, that application's runoff returns `status: "met"`, `required: false`, `exempt: true`, `required_points: 0`, and `gap: 0`. `label_required_points` retains the original target (or null if unresolved); earned credits and the saved exemption timestamp/reasons remain visible. Missing soil or an unresolved point target does not block an exempt runoff obligation.
- Choosing “None apply” in the portal restores the point requirement. Rechecking the same application preserves its portal selection. A new application starts required, even on the same field.
- Older `required: false` records without an exemption evaluation timestamp are treated as required. Timestamped legacy exemption selections without reason codes are honored.

Exemptions apply to EPA runoff only. Enlist, other runoff systems, drift, and PULA restrictions are still assessed separately, so a runoff exemption does not automatically make the entire application compliant. No request-body exemption flag is accepted; the portal records the user's selection.

These rules also apply to [bulk checks](/v2/api-reference/endpoint/bulk-submit). After a portal edit, use [application compliance](/v2/api-reference/endpoint/application-compliance) or [group compliance](/v2/api-reference/endpoint/group-compliance) for current runoff results. Previously returned checks and completed bulk results remain snapshots; resubmit a check to refresh its saved assessment.

## Drift assessment

Single and bulk ESA checks identify drift requirements and reductions. They do not calculate application-time buffer placement or accept wind inputs. When a drift requirement exists and no known violation is found, intake drift remains `indeterminate` until you call [compute application-time drift buffers](/v2/api-reference/endpoint/drift-buffer) with the application reference and current wind/setup. A known violation, such as droplets below the label minimum, returns drift and overall `not_met` immediately, even if other inputs remain unresolved.

The application-time endpoint can return drift `met` with a remaining buffer: your supplied setup complies when spraying stays within the calculated treatable area. A 100% buffer reduction is not required. Its `application_time.drift_status` is separate from the overall `application_time.status`. Repeating an intake check produces a new intake assessment; recompute application-time drift afterward to assess placement for the new inputs.

## Repeat a check

The provider/account/application identity is reused. Resubmitting updates the saved assessment when ESA processing is required. A no-ESA early return does not update an existing saved application. A changed field boundary refreshes its derived data. Background soil enrichment requires a new check to refresh the assessment.

## Errors

Processing can return `409 DUPLICATE_FIELD`, `FIELD_OWNERSHIP_CONFLICT`, `DUPLICATE_APPLICATION`, `APPLICATION_FIELD_CONFLICT`, `PROCESSING_CONFLICT`, `FIELD_CHANGED`, or `APPLICATION_CHANGED`. Signed portal setup can return `503 PORTAL_SAS_UNCONFIGURED`. A workflow can also return `422 UNSUPPORTED_APPLICATION_METHOD`; HTTP input validation normally catches this first as `INVALID_REQUEST`. See [assessment issues](/v2/errors#assessment-issue-codes) for incomplete evidence returned with HTTP 200.

All routes can also return [authentication, validation, rate-limit, and dependency errors](/v2/errors#http-error-catalog). Use the [error catalog and examples](/v2/errors) to choose a retry or correction. Keep `X-Request-ID` when present.
